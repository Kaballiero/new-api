# server/internal — правила структуры

Стремимся к структуре по бизнес-сценариям внутри самостоятельных модулей. Каждый сценарий читается сверху вниз: HTTP → usecase → узкие интерфейсы → технические адаптеры.

## Структура

```
server/internal/
  accounts/
    create_account/
      dto.go
      http.go
      usecase.go
    update_account/
      dto.go
      http.go
      usecase.go
    domain/
      account.go
      errors.go
    dto/            # только общий wire-формат ≥ 2 сценариев
    transport/      # только общий входящий HTTP ≥ 2 сценариев

  identity/
  apikeys/
  pricing/

  adapter/
    gorm/
      accounts/
    http/           # только исходящие HTTP-клиенты
    redis/

  app/
    accounts.go
    identity.go
    pricing.go

  contracttest/     # общая заготовка контрактных HTTP-тестов (не модуль)
```

- Модуль объединяет самостоятельную бизнес-область: `accounts`, `identity`, `pricing`.
- Пакет сценария соответствует конкретному действию. Названия понятные и однозначные, без вариантов вроде `checkin` и `check_in`.
- Внутреннему сценарию без собственного HTTP и самостоятельных DTO достаточно `usecase.go`.
- Пустые файлы и папки «на будущее» не создаём.
- В корне модуля нет `.go`-файлов: только папки сценариев, `domain/` и при необходимости `dto/` и `transport/`.

### Имена сценариев

- Имя — `глагол_объект`: `create_account`, `reset_password`.
- Если одно и то же действие есть у разных исполнителей (в том числе в разных модулях), оба имени уточняются: `admin_<действие>` и `<действие>_own_<объект>` — например, `admin_delete_account` и `delete_own_account`.
- Если варианта для другого исполнителя нет, префикс не ставим: права описывают маршрут и authz, а не имя пакета.

## Ответственность файлов

| Файл / слой            | Что содержит |
|------------------------|--------------|
| `http.go`              | Разбор запроса, контекст доступа, вызов usecase, формирование прежнего HTTP-ответа |
| `dto.go`               | Реальные входные и выходные структуры конкретного сценария |
| `usecase.go`           | Бизнес-проверки, последовательность действий, границы транзакций и порядок побочных эффектов |
| `domain/`              | Общие бизнес-понятия, значения, правила и бизнес-ошибки без транспорта и ORM |
| `<module>/dto/`        | Wire-формат (JSON запроса/ответа), реально общий для ≥ 2 сценариев модуля: структуры и преобразования в/из domain, без логики |
| `<module>/transport/`  | Входящий HTTP, общий для ≥ 2 сценариев модуля: сопоставление ошибок domain с HTTP-ответом, разбор параметров запроса |
| `adapter/`             | SQL, GORM, Redis, исходящие HTTP-клиенты, технические блокировки, CAS, chunking, сериализация хранимых полей и преобразования |
| `app/`                 | Создание реализаций, явная сборка зависимостей, запуск фоновых задач |

Usecase определяет, что должно выполниться атомарно. Адаптер реализует конкретную транзакцию и особенности движка БД.

Входящий HTTP — запросы к нашему API; его код живёт в `http.go` сценария и в `<module>/transport/`. Исходящий HTTP — наши обращения к внешним системам; его код живёт в `adapter/http/`. Код, используемый одним сценарием, остаётся в его `http.go` / `dto.go`.

## Зависимости

- Узкий интерфейс объявляется рядом с его потребителем.
- Конструктор получает все зависимости явно.
- Поля зависимостей usecase закрытые; создание через `NewUsecase`.
- Метод запуска сценария — `Execute`. Разнобой `Run` / `Execute` убираем.
- Сценарии не вызывают друг друга напрямую. Общие правила принадлежат `domain`; координация — сценарию, который владеет всем процессом.
- Общие типы и контракты появляются только при конкретных потребителях.

Не вводим глобальные service locator, скрытую инициализацию, generic repositories, универсальные CRUD-фасады и command bus.

### Что можно импортировать

- **`usecase.go` и любые другие файлы сценария, кроме `http.go` и `dto.go`**: не импортируют Gin, GORM, Redis-клиенты, `model`, `service` и `internal/adapter`.
- **`http.go` и `<module>/transport/`**: только транспорт — стандартная библиотека, Gin, `common`, `i18n`, `constant`, `domain`/`dto`/`transport` своего модуля и `domain` модуля-владельца. Всё остальное (`model`, `service`, `setting`, `middleware`, `logger`, сторонние библиотеки, GORM, Redis, `internal/adapter`, соседние сценарии) приходит через конструктор из `app`.
- **`domain/` и usecase не зависят от транспорта, ORM и Redis даже транзитивно** (проверяется `go list -deps`). Поэтому `domain` не импортирует пакеты, которые тянут Gin/GORM/Redis (сейчас это `common`), не сериализует хранимые поля (это задача адаптера) и не пишет логи.

### Как передавать зависимости

- Хранилища, кэши, внешние клиенты, аудит — узкие интерфейсы.
- Настройки, часы, генераторы — функции (`func() int`, `func() int64`): так сохраняется позднее чтение настроек.
- Если функций больше трёх, группируем их в именованную по смыслу структуру: `KeyLimits{MaxQuota, MaxTokens func() int}`.

### Форма `Execute`

- Вход: `ctx` первым, если нужен; дальше один примитив или структура `Input` при двух и более параметрах.
- Выход: `error` или `(результат, error)`.
- Ошибка возвращается только через `error`. Структуры вида `Result{Cause: err}` или `*Failure{Kind}` не используем.

### Ошибки

- Бизнес-ошибки — значения или типы в `<module>/domain` (`var ErrPasswordState = errors.New(...)`).
- Usecase возвращает `error`; `http.go` / `transport` сопоставляет его через `errors.Is` / `errors.As` со статусом, кодом и i18n-сообщением.
- Ошибки преобразуются в HTTP на транспортной границе; бизнес-логика не формирует Gin-ответы.
- Если старые потребители сравнивают ошибку с `model.Err*` / `common.Err*`, старое имя становится алиасом: `var ErrAccountPasswordState = domain.ErrPasswordState`. Фабрики ошибок (`func() error`) в конструктор не передаём.
- Текст, который уходит клиенту в HTTP-ответе, не захардкожен: он берётся из backend i18n (`i18n/locales`, ключ `i18n.Msg*`) на транспортной границе. Каждый новый ключ добавляется минимум в `en.yaml` и `ru.yaml`; `zh-CN`/`zh-TW` сохраняются и при отсутствии ключа падают на `en`. Английский текст существующих ответов остаётся побайтно прежним.
- Внутренние ошибки, которые попадают только в лог или оборачиваются (`fmt.Errorf("...: %w", err)`), остаются обычными `errors.New`/`fmt.Errorf` на английском.
- Переводим на i18n по модулям, по ходу их чистки, а не единым проходом по всему backend.

### Зависимости между модулями

1. **Владелец понятия.** У каждого бизнес-понятия один модуль-владелец — тот, кто его хранит, изменяет и отвечает за его инварианты.
2. **Зависимость направлена к владельцу.** Модуль может импортировать `domain` модуля-владельца, когда использует его понятие как данность. Владелец не знает о потребителях.
3. **Направление — от производного к базовому.** Импортирует тот, чьё понятие строится поверх чужого (цена поверх модели и канала; аутентификация поверх аккаунта).
4. **Встречная потребность — сигнал ошибки в границах.** Если двум модулям нужны понятия друг друга, понятие лежит не там: его переносят к настоящему владельцу или выделяют, а не обходят импортом. Циклы недопустимы даже там, где их не заметит компилятор (через `app` или адаптеры).
5. **Чужое только читаем; изменяем через владельца.** Из чужого модуля импортируется только `domain` — не сценарии, `dto`, `transport`, корень модуля или адаптеры. Если сценарию нужно изменить чужие данные, он объявляет узкий интерфейс у себя, а реализацию на стороне владельца подключает `app`; инварианты проверяет владелец.

## Граница со шлюзом

`server/internal/` — бизнес-модули. Шлюз к AI-моделям (`relay/`, `relaykit/`, relay-цепочка `middleware/`) — заменяемая реализация: впоследствии её заменит собственный сервис. Поэтому контракт принадлежит бизнесу.

- Бизнес-модули не импортируют `relay` и `relaykit`. Типы, которыми бизнес обменивается со шлюзом, — свои, в `domain`.
- Что шлюзу нужно от бизнеса (проверка ключа, резерв и расчёт квоты, конфигурация каналов, цены, запись использования) — обычные сценарии владельцев в `internal`. Шлюз вызывает их, а не `model`/`service`.
- Что бизнесу нужно от шлюза (тест канала, загрузка моделей upstream) — узкий интерфейс в сценарии-потребителе; реализация — `adapter/gateway/<реализация>/`, выбор — в `app`.
- Связь обеих сторон знает только `app`.

## Фоновые задачи

- Один прогон задачи — обычный сценарий: `usecase.go` с `Execute(ctx)`, без `http.go`. Он не знает о тикерах и кластере.
- Расписание, тикер, `common.IsMasterNode`, защита от параллельного запуска, recover и логирование результата — в `app/<module>.go` (`Start<Task>`).
- `main.go` вызывает `app.Start<Task>()`.
- Интервалы, порядок шагов, тексты логов и master-only поведение сохраняются.

## Сборка и мосты

- Зависимости модуля собираются один раз при старте, а не на каждый запрос. Пока роутер вызывает контроллер, мост в `controller/` держит сборку через `sync.OnceValue`; когда мостов не остаётся, сборка переезжает в router. Данные запроса (`gin.Context`) передаются в `Handle`, а не в конструктор.
- `model` и `service` не создают и не запускают usecase. Usecase создаёт только `app`, транзакцию реализует `adapter/gorm`. Если адаптеру нужен приватный хелпер `model` (например, блокировка строк), его экспортируют. Существующие случаи — долг, новые запрещены.
- **Мост по умолчанию не нужен:** сценарий переносится вместе со всеми потребителями в одном изменении. Мост допустим только для потребителя вне текущего переноса (например, в ещё не перенесённом модуле). Мост живёт на стороне потребителя или в `controller/`; в `model`/`service` новые мосты не создаются — они импортировали бы `internal`, а `internal/app` сам импортирует `service`. Мост не содержит логики, помечается в коде `// BRIDGE: <кто вызывает>` и обязательно перечисляется в описании изменения. Мост удаляется, когда у него не остаётся потребителей.
- Модуль считается перенесённым, когда в `controller/` для него остались только однострочные пробросы и алиасы типов для существующих потребителей, а импорты `internal` из `model`/`service` по этому модулю убраны из списка исключений архитектурного теста.

## Стиль кода

- Прямой последовательный код, ранние возвраты, небольшая вложенность.
- Конкретные имена по смыслу операции: `AccountStore`, `SessionRevoker`, `QuotaCache`.
- Интерфейсы содержат только необходимые потребителю методы.
- Не дробим код на одноразовые механические функции ради сокращения основного метода.
- Выделяем функции для повторного использования, самостоятельного бизнес-правила, сложного алгоритма или требуемого callback.
- Избегаем вложенных функций, кроме оправданных callbacks.
- Используем современные возможности Go из версии модуля, `gofmt` и проектные JSON-обёртки.
- Комментарии в Go-коде — на английском, как в остальном проекте. Русские комментарии в перенесённом коде переводим на английский при чистке модуля. Документы правил (`AGENTS.md`) остаются на русском.

## Тесты

- Основа — контрактный HTTP-тест модуля (`internal/<module>/contract_test.go`): маршрут → статус и JSON, включая ответы без авторизации и с недостаточными правами (401/403). Он пишется на старом коде как baseline и остаётся зелёным после переноса.
  - Контрактный тест есть у `apikeys`. Для остальных модулей контрактные тесты не пишем: достаточно существующих тестов, сравнения маршрутов/цепочек middleware/OpenAPI с `origin/main` и тестов usecase (ниже).
  - Заготовка — `internal/contracttest`: `contracttest.New(t)` поднимает БД через production `model.InitDB`/`InitLogDB`, production-лимиты, middleware `RequestId`/`I18n`, настоящий `router.SetApiRouter` и пользователей с живыми сессиями (`env.User`, `env.Admin`, `env.Root`, `env.UserPAT`, `contracttest.Anonymous`); `env.Do(...)` отправляет запрос; `contracttest.Golden(t, name, recorder, dynamicKeys...)` сравнивает статус, `Cache-Control`/`Retry-After` и тело с `testdata/golden/<name>.golden.json`; `contracttest.GoldenValue(t, name, env.AuditLog(t), ...)` фиксирует побочные эффекты аудита.
  - Эталоны записываются на коде **до** переноса флагом `-update` (как в `relaykit`): для уже перенесённого модуля — во временном worktree `origin/main`, куда копируются `internal/contracttest` и `contract_test.go`; затем эталоны копируются в ветку и тест без `-update` должен быть зелёным. Расхождение — изменение поведения переносом, его разбираем. При дальнейшей работе эталоны не перезаписываются и не правятся; изменение эталона — это изменение контракта, его обсуждаем отдельно.
  - Меняющиеся значения перечисляются в `dynamicKeys` и маскируются с сохранением формы: буквы и цифры строки → `x` (длина и разделители сохраняются, поэтому маска ключа и полный ключ различаются), числа → `__number__`, булевы → `__bool__`; объекты и массивы сохраняют структуру.
  - Контрактные тесты запускаются с `-count=1`: in-memory rate limiter общий для процесса.
  - Ограничения заготовки: только SQLite (после неё в том же пакете не запускать тесты на других диалектах — колонки диалекта не пересчитываются); production `CustomRecovery` из `main.go` не подключён, поэтому паника в обработчике роняет тест, а не фиксируется как ответ 500.
- Тест usecase на подставных реализациях узких интерфейсов. Сценарии и ожидания берём из тестов того же поведения в `origin/main` (controller/service/model): те же входы и те же выходы, ошибки и побочные эффекты, но на уровне usecase. Логика и выходные данные совпадают — значит, поведение сохранено. Тривиальные сценарии (чтение без правил) отдельного теста не требуют.
- Тесты `adapter/gorm` — на реальном PostgreSQL, когда затронуто хранение.
- Старые тесты `controller/` / `service/` переезжают вместе с логикой, а не копируются.
- Действуют правила тестов из корневого `AGENTS.md` (без тестов ради покрытия, `testify/require` + `assert`).

## Автоматическая проверка

`internal/architecture_test.go` проверяет правила импортов: `usecase.go`, `http.go`/`transport`, транзитивную чистоту `domain` и usecase, импорт только `domain` из чужих модулей, отсутствие `.go` в корне модуля, отсутствие новых импортов `internal` из `model`/`service`, отсутствие новых импортов `relay`/`relaykit` из `internal`. Текущие нарушения — явный список исключений, который только уменьшается.

- Список исключений — `internal/architecture_known_violations_test.go`. Исправил нарушение — удали строку: тест падает и на устаревшей записи. Новые записи не добавляем.
- Текущие нарушения печатает `ARCH_TEST_PRINT=1 go test -run TestInternalArchitecture ./internal`.
- Транзитивные правила (`usecase-transitive`, `domain-transitive`) проверяются по `go list -deps`; одна запись на файл или пакет.

## Документация модулей

Документацию проекта пишем по ходу работы, рядом с кодом, на русском:

- `server/internal/README.md` — карта: список модулей, одна строка об ответственности каждого, граница со шлюзом, где искать сборку (`app/`) и адаптеры.
- `server/internal/<module>/README.md` — для каждого модуля:
  - **Ответственность** — какую бизнес-область покрывает и какими понятиями владеет (источник истины).
  - **Возможности** — сценарии модуля: имя пакета, что делает, HTTP-маршрут и кто может вызвать (роль, сессия/PAT), либо фоновая задача.
  - **Зависимости** — чей `domain` использует и почему; кто использует этот модуль; какие узкие интерфейсы реализуют адаптеры.
  - **Границы и долг** — что модулю не принадлежит, известные исключения архитектурного теста и мосты.
- README модуля создаётся или обновляется в том же коммите, что и чистка или перенос модуля. Описываем фактическое поведение, а не планы.

## Совместимость и завершённость

Рефакторинг сохраняет маршруты, порядок middleware, права, JSON, статусы, ошибки, defaults, nil/zero/false, поздние чтения настроек, транзакции, блокировки и порядок побочных эффектов. Исходные баги попутно не исправляем. HTTP-контракт API не меняется.

Исключение — критичные находки: баг, который съедает память или ресурсы (утечка горутин, неограниченный рост кэша, незакрытые ресурсы), ломает данные или безопасность, а также оптимизация без изменения схемы БД. Их не чиним молча: описываем (где, сценарий, последствия, предлагаемое исправление и как оно меняет поведение) и ждём решения. Принятое исправление — отдельный коммит с тестом, который воспроизводит проблему, и отдельный пункт в описании PR.

Совместимые мосты оставляем только для существующих потребителей (см. «Сборка и мосты»). Новая логика принадлежит новому владельцу — параллельных реализаций одного сценария быть не должно.

**До переноса (baseline):**
- `make test` — зелёный;
- `make openapi-check` — зелёный;
- контрактный HTTP-тест модуля написан и зелёный на старом коде.

**После переноса:**
- `go -C server vet ./...` и `make test`;
- `make openapi-check` — без изменений;
- `cd server/relaykit && GOWORK=off go build ./...`;
- архитектурный тест зелёный, список исключений не вырос;
- при затрагивании хранения — реальный PostgreSQL (рабочая БД платформы), версия и команды в отчёте; SQLite и MySQL локально не проверяются;
- независимое ревью свежим исполнителем.
